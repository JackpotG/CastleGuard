# 04 环境搭建与工具链（M0 排雷记录）

> 2026-11-13 实测完成。本文既是一次搭建记录，也是理解整条构建链路的讲义。
> 目标读者：未来的自己。重装机、换电脑、或者某一步突然报错时，回来看这篇。

## 一、工具链全景：一行 C++ 代码的旅行

```
你写的 C++ 代码（code/axmol/CastleGuard/Source/）
    │
    ▼
Axmol 引擎源码（engine/axmol/）   ← 渲染、音频、输入、场景树都在这，源码全开放
    │
    ▼
CMake + Ninja + clang            ← 构建系统 + 构建执行器 + 编译器
    │
    ├─ 桌面：.app 可执行程序（Ninja 生成器 + 命令行工具 CLT，不需要完整 Xcode）
    │
    ▼
Emscripten (emsdk 3.1.73)        ← 同一套 C++ 交叉编译成 WASM + WebGL
    │
    ▼
浏览器 H5 包（.html/.js/.wasm/.data）
    │
    ▼
wx-transformer（微信转换工具）     ← 改胶水代码、生成小游戏工程结构、压缩 wasm
    │
    ▼
微信小游戏包（wechat-build/minigame/）→ 微信开发者工具 → 真机
```

### 每个组件的角色

| 组件 | 干什么 | 关键认知 |
|---|---|---|
| **Axmol** | cocos2d-x 4.0 社区维护分支，提供场景树/精灵/渲染器/音频 | 引擎即源码，学渲染管线直接读 `engine/axmol/core/renderer/` |
| **CMake** | 一份构建描述生成各平台工程 | axmol 的所有平台差异都收敛在 `engine/axmol/cmake/` 里 |
| **Ninja** | 比 Make 更快的构建执行器 | axmol 各平台默认生成器（macOS 官方默认 Xcode，我们用 `-xc "-G,Ninja"` 覆盖） |
| **Xcode CLT (clang)** | macOS 系统编译器 | **只装命令行工具就够用**；完整 Xcode 只有要生成 .xcodeproj、做 iOS 签名时才需要 |
| **PowerShell (pwsh)** | 跑 axmol 的跨平台安装/构建脚本 | axmol 用 PowerShell 统一三平台脚本；macOS 上用免安装版（见坑 2） |
| **axmol CLI** | `axmol new` 建项目 / `axmol build` 编译 / `axmol run` 运行 | 入口在 `engine/axmol/tools/cmdline/axmol` |
| **emsdk** | Emscripten 工具链管理器，把 C++ 编成 WASM | 版本要锁（见排雷 5），axmol 按项目 `.axproj` 里的 `emsdk=` 自动下载对应版本 |
| **wx-transformer** | 微信官方 WASM→小游戏转换工具 | 输入 H5 三件套（js/wasm/data），输出 minigame 工程 |
| **微信开发者工具** | 小游戏模拟器 + 调试器 | 用 Stable 版，不是"小游戏版" |

### 一个值得记住的设计：工具链自包含

Axmol 的 setup 会把自己锁定版本的工具（axslcc 着色器编译器、emsdk 等）下载到 `engine/axmol/tools/external/`，不用系统版本。这保证了换机器、换人后构建结果一致——专业团队的标配做法。

## 三、常用命令速查

```bash
# 所有 axmol 命令都需要这两个环境变量（已写入 ~/.zshrc，新终端自动生效）
export AX_ROOT=<项目绝对路径>/engine/axmol
export PATH="$AX_ROOT/tools/external/powershell:$PATH"

# 编译桌面版（注意：-xc 传配置参数，-xb 传构建参数，别搞混）
axmol build -p osx -a arm64 -xc "-G,Ninja"

# 编译 + 浏览器运行 WASM 版
axmol run -p wasm

# 编译微信用 WASM（关线程，见坑 6）
axmol build -p wasm -xc "-DAX_WASM_THREADS=off"

# 转换为微信小游戏
<项目>/tools/wechat/wx-transformer/wx-transformer-v1.0.35-macos \
  --config <项目>/code/axmol/CastleGuard/wechat-transform.config.json

# ⚠️ 从 Kimi/其他 Electron 应用的终端里启动微信开发者工具，必须：
env -u ELECTRON_RUN_AS_NODE /Applications/wechatwebdevtools.app/Contents/MacOS/wechatwebdevtools &
```

## 四、排雷记录（每个坑的根因）

### 1. git clone 报 `HTTP2 framing layer`
网络代理对 HTTP/2 支持有问题。解法：`git -c http.version=HTTP/1.1 clone ...`，curl 对应 `--http1.1`。

### 2. PowerShell 官方 pkg 装不上（需要 sudo）
brew cask 和 axmol 自带 `1k/pwshi.sh` 都走 pkg 安装，都要管理员密码。
解法：改用**免安装 tar.gz**，解压到 `engine/axmol/tools/external/powershell/` 加进 PATH 即可，与 pwshi.sh 的 Linux 分支同款思路。

### 3. setup.ps1 强检 xcodebuild
`1k/1kiss.ps1` 的 `setup_xcode()` 找不到 xcodebuild 直接 throw。但分析发现：xcodebuild 只在 Xcode 生成器路径真正需要，CMake 里唯一调用点被 `if(XCODE AND ...)` 守卫。
解法：本地补丁把 throw 改成 warning（已在 `1kiss.ps1` 标注 "Local patch"），构建时 `-xc "-G,Ninja"` 绕开 Xcode 生成器。
**注意**：升级引擎后补丁会被覆盖，需要重打。

### 4. 桌面版启动报 `Library not loaded: soft_oal.framework`
OpenAL Soft 音频框架编译出来了，但"拷贝进 .app 的 Frameworks 目录"这步也是 Xcode 生成器专属逻辑，Ninja 路线漏掉了。
解法：手动拷贝 + 重签名：
```bash
cp -R build/engine/3rdparty/openal/soft_oal.framework \
  build/bin/CastleGuard/CastleGuard.app/Contents/Frameworks/
codesign --force --deep -s - build/bin/CastleGuard/CastleGuard.app
```

### 5. emsdk 3.1.51 编译失败：`AL/alext.h not found`
微信适配文档推荐 emsdk 3.1.51，但 axmol 音频层 `oal_port.h` 在 `__EMSCRIPTEN__` 下包含 `AL/alext.h`，而 **emscripten 直到 3.1.73 才自带这个头文件**（3.1.51/3.1.53 均没有）。
结论：改用 axmol 官方默认的 **3.1.73**（`.axproj` 里 `emsdk=3.1.73`）。
**遗留风险**：微信能力 SDK 只提供 emsdk3.1.10/3.1.51 预编译变体，未来集成 SDK（网络/文件系统/音频适配）时可能有 ABI 兼容问题，届时需要实测或向微信反馈群求新版。

### 6. `AX_WASM_THREADS=0` 竟然不关线程
CMake 里判断条件是 `MATCHES "^([0-9]+)$"`——`"0"` 也匹配数字，照样开 pthread！
解法：传**非数字**值 `-DAX_WASM_THREADS=off`。
为什么必须关：pthread 依赖 SharedArrayBuffer，微信小游戏环境不支持。微信适配的其他约束：主包 JS ≤ 2MB、建议固定 INITIAL_MEMORY 关闭内存动态增长（当前 axmol 默认 128MB + ALLOW_MEMORY_GROWTH=1，M0 先跑通，后续再按微信平台要求收严）。

### 7. 微信开发者工具启动即退（Kimi 环境变量污染）
根因：**Kimi 桌面端（Electron 应用）会给子进程环境注入 `ELECTRON_RUN_AS_NODE=1`**，导致开发者工具的 NW.js 运行时以 Node 模式静默退出。
解法：`env -u ELECTRON_RUN_AS_NODE` 前缀启动。从正常终端（Terminal.app）直接双击打开无此问题。

### 8. 开发者工具弹窗「当前应用已损坏，请重新下载安装」（官方打包 bug）
根因：Stable 2.02.2609250（2026-11-06，首个 Electron 内核稳定版）的 macOS arm64 包里**没有 `Contents/Resources/package.nw/consistency.dat`**，但 NW.js 时代遗留的 Go 启动器仍强制校验这个文件（见官方日志 `~/Library/Application Support/微信开发者工具/<hash>/WeappLog/launch.log`），自检失败即弹窗退出。重新下载无效（dmg 里本来就没有），与 Gatekeeper/签名/quarantine 全部无关。
解法：绕过 Go 启动器，直接启动 Electron 内核：
```bash
cd /Applications/wechatwebdevtools.app/Contents
nohup env -u ELECTRON_RUN_AS_NODE ./MacOS/Electron >/tmp/wxdev.log 2>&1 &
```
代价：每次启动都要走这条路径（或等官方修复，可关注 Nightly）。注意 CLI（`Contents/MacOS/cli`）不受此影响。

### 9. CLI 导入报「项目路径不存在」/「登录用户不是该小程序的开发者」
两个独立小坑：
- CLI 的 `--project` 只接受**已存在**的路径；wx-transformer 的 `output` 参数若没传，产物实际落在**转换器自己所在的目录**下（`tools/wechat/wx-transformer/wechat-build/`），不是配置里写的路径。
- 「不是开发者」多数情况是**登录态陈旧**：刚在 mp 后台改完账号信息（类目、权限）后，必须在开发者工具里**退出登录重新扫码**才能生效。

### 10. 导入报「app.json 未找到」——项目被当成小程序了
根因：项目管理窗口默认停在「小程序」标签页，从那里导入会强制 `compileType=weapp`（日志可见 `compileType changed old=game new=weapp`），分配的测试号也是小程序测试号。
解法：必须先切到**「小游戏」标签页**再导入。`touristappid` 在新版已失效（报「不存在此 AppID」），不要再用。

### 11. 「插件未授权使用」——测试号死路，必须正式小游戏账号
wx-transformer 产物的运行依赖官方插件 **WXGameKit**（`wxe5a48f1ed5f544b7`，wasm 加载/文件系统/启动页全靠它）。微信规则：插件必须在 mp 后台「管理 → 插件管理」添加授权；**测试号没有后台，永远加不了插件**。
解法：注册正式小游戏账号——入口是 mp.weixin.qq.com 的**「小程序」注册**（没有独立小游戏入口），注册后补服务类目：一级「游戏」（选定不可改）+ 二级「休闲」（个人主体不能选角色/棋牌/文化互动）。已有小程序账号若类目为空可直接补类目转小游戏。拿到 AppID 后在「插件管理」搜 `wxe5a48f1ed5f544b7` 添加（官方插件即时生效）。
注意：WXGameKit 名义上是「Unity 插件」，实为**引擎无关的 WASM 运行时套件**，Cocos2dx/Axmol 同样使用，不要被名字误导。

### 12. `Unexpected end of JSON input`——产物里的 appID 是默认值
根因：wx-transformer 不传 `--app-id` 时会把内置默认号（如 wx79dd...）写进产物 `wx-game-kit/config.json`，WXGameKit 拿这个不属于我们的号拉远程配置拿到空响应，`JSON.parse('')` 爆炸。
解法：转换配置里显式传 `"appID"`，且**三处必须一致**：`project.config.json` 的 appid、`wx-game-kit/config.json` 的 appID、源转换配置的 appID。换号时三处一起改。

### 13. `Cannot read properties of undefined (reading 'open')` + `fetch is not defined`（wx-transformer 对 Cocos2dx 适配不全）
根因：wx-transformer v1.0.35 生成 `framework.js` 时，定义了 `Module.getPreloadedPackage()` 却**忘了调用**，Emscripten 的浏览器资源装载流程（IndexedDB 缓存 + fetch 下载）原样保留——小游戏环境这两个 API 都不存在。
更深一层时序坑：WXGameKit 把数据包放进 `Module.rawData` 后调用自定义处理器，**回调一返回就把 `rawData` 置 null**；而 Emscripten 侧是经 `preRun` 延迟消费的，读到时已是 null。
解法（产物补丁，重跑转换器会丢失，需重打）：在 `framework.js` 的 `setCustomProcessRawDataHandler` 回调**入口立即捕获** `var _cgRawData = Module.rawData;`，并在 `runWithFS` 尾部用 `if (_cgRawData) processPackageData(_cgRawData); else openDatabase(...)` 跳过浏览器流程。产物中搜 `[CastleGuard patch]` 可定位两处补丁。
经验：给上游提 issue 前先在 GitHub `wechat-miniprogram/minigame-unity-webgl-transform` 查新版转换器是否已修。

### 14. 模拟器里弹「timelog」白色弹窗
不是错误，是 WXGameKit 的**启动耗时报告**（开发期诊断），由产物 `wx-game-kit/config.json` 的 `develop.hideTimeLogModal: false` 控制。看到 `callMain耗时` 和 `游戏启动耗时` 即代表游戏启动成功。嫌烦可改为 `true`。

### 15. 其他零碎
- 本版开发者工具 macOS 快捷键：`Cmd+B` 是切换侧边栏，**编译要点工具栏「编译」按钮**。
- CLI 需要先在「设置 → 安全设置」开启**服务端口**。
- 编译报 `spawn ...wechatwebdevtools Helper ENOENT` 且文件实际存在：多半是打开的工程指向了**已被移动/删除的旧路径**（spawn 的 cwd 不存在也会报 ENOENT），关掉旧窗口从新路径重新导入即可。
- 产物里的 timelog 弹窗（`develop.hideTimeLogModal`）与"优化建议"弹窗（`develop.monitor.*`）都是 WXGameKit 开发期功能，跑通后可关。

### 16. `window.matchMedia is not a function`（引擎启动即崩）
根因：小游戏 JS 环境没有 CSS 媒体查询 API，而 Axmol `RenderViewImpl::initWithRect` 用 `matchMedia('(pointer: coarse)')` 判断是否触屏设备。
解法：产物新增 `cg-compat.js` 环境垫片并在 `game.js` **首行**引入——小游戏 100% 是触屏，polyfill 固定返回 coarse=true、hover=false。
经验：这类"浏览器 API 不存在"的崩溃，用最小 polyfill 补环境，不要去改引擎。

### 17. 画面元素挤到右上角、HelloWorld 不可见（三层尺寸错位）
根因：三层尺寸各说各话——引擎窗口=AppDelegate 写死的 720×1280（canvas 缓冲区跟随），微信按物理分辨率显示，window 垫片的 innerWidth/DPR 未初始化全部按 1.0 回退，坐标映射整体错乱。
解法（产物补丁）：劫持 `GLFW.createWindow`，把窗口尺寸强制为 `screenWidth × pixelRatio`（物理分辨率），canvas 缓冲区随之等于物理屏，设计分辨率 720×1280 经 SHOW_ALL 策略自动缩放居中。补丁打在 framework.js 的 `createWindow` 开头（搜 `[CastleGuard patch]`）。
排查方法论：不要盲目调参数，先打诊断日志拿三层真实值（`wx.getSystemInfoSync` / window 垫片 / `canvas.width`）再对齐——本次靠 `[CG-DIAG]` 三行日志一次定位。

### 18. 「登录用户不是该小程序的开发者」反复出现——AppID 的三处藏身地
现象：产物里 `project.config.json` 的 appid 明明已修正，开发者工具仍反复弹此提示。
根因：AppID 有三个独立来源，只修一处没用——
1. **产物 `project.config.json`**：wx-transformer 每次转换都重置为内置默认号 `wx80127…`，补丁脚本（补丁 6）已永久解决；
2. **工具的 `WeappLocalData` 项目清单**（`localstorage_…914f….json` = reduxPersist:projectList）：工具按路径记忆 AppID，曾经用错误号打开过就会被记住；可在弹窗的 AppId 下拉框手改成正确号点确定，或关工具后直接改 JSON；
3. **工具的 Chromium Local Storage**（`Local Storage/leveldb`）：提示框真正读取的地方，前两处修好后它还会复活提示。解法：关工具，删除（或移走备份）`~/Library/Application Support/微信开发者工具/Local Storage` 目录，重启后工具从产物配置重建。
根治顺序：先保产物正确（补丁 6），再清工具的两处记忆。注意清缓存可能需重新扫码登录。

### 19. 改 AppID 后模拟器黑屏、随后整个工具白屏（实例状态损坏）
现象：重导入工程后，游戏控制台日志全部正常（wasm 编译耗时、callMain、启动耗时都在），画面却纯黑；之后整个开发者工具窗口白屏。
根因：工具重新初始化过程中渲染进程崩溃，但**主进程没死**，占着 Electron 单实例锁——之后每次启动都只是"唤起已有（白屏）窗口然后退出"（日志可见 `已有运行中的实例，已唤起已有窗口，本次启动退出`）。
处置：
```bash
# 1. 找到并强杀主进程（./MacOS/Electron，而不是 Helper 子进程）
ps -o pid,etime,command -p $(pgrep -f wechatwebdevtools)
kill -9 <主进程PID>
# 2. 清模拟器内核缓存（不影响工程与登录）
rm -rf ~/Library/Application\ Support/微信开发者工具/Partitions/simulator_*
# 3. 冷启动
cd /Applications/wechatwebdevtools.app/Contents && nohup env -u ELECTRON_RUN_AS_NODE ./MacOS/Electron &
```
排查方法论（本次的最大教训）：① 先做**对照实验**再改代码——把怀疑的新代码禁用后黑屏依旧，说明病根在环境不在代码；② 先分层——控制台无报错且启动日志齐全 = 逻辑层活着、渲染层/工具侧坏了，别去翻游戏代码。
