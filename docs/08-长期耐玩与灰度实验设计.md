# 08 长期耐玩、菜单与灰度实验设计

> 状态：设计草案 V1（2026-11-18）。本文件定义 M2 后半段的产品化方向；具体数值仍以测试结果调整。
> 战斗成长、武器换装、城墙与被动防御的详细设计见 `docs/09-战斗成长与装备系统设计.md`。

## 一、先明确问题：耐玩不等于堆更多关

当前版本已经有 13 种怪物、5 关战役、无尽模式和两套三选一。继续手写更多“数量更大、血量更高”的关卡，会重复原作后期的问题。长期耐玩需要四层同时成立：

1. **战斗层有组合变化**：怪物职责、出生编队、精英词缀和战场规则改变应对方式。
2. **关卡层有学习节奏**：介绍一个机制、单独检验、组合检验、反转、章节考试。
3. **局外层有长期目标**：升级、章节进度、挑战徽章、图鉴和模式成绩提供不同目标。
4. **运营层能验证和调整**：稳定 A/B 分组、事件埋点、远程配置与灰度回滚让设计可以被数据纠正。

因此本阶段的目标不是“尽可能多写 JSON”，而是先建立一套可持续生产内容的规则。

## 二、首发内容目标

首发基线建议从 5 关扩展到 **4 章 × 5 关 = 20 关**。现有 5 关作为机制验证样本，扩关时重新分配怪物出场顺序，避免第 5 关前一次性塞完 13 种怪物。

| 章节 | 主要教学与压力 | 主要怪物 | 章节考试 |
|---|---|---|---|
| 第一章·城下试探 | 点射/连射、优先目标、两翼出怪 | 普通、快速、远程 | 第一只先锋 Boss |
| 第二章·铁壁爆潮 | 破防、范围伤害、数量膨胀 | 护盾、自爆、分裂 | 护盾编队 + 分裂潮 |
| 第三章·寒雾战线 | 空地双线、治疗链、目标消失 | 飞行、治疗、狂暴、幽灵 | 治疗护航 + 幽灵突袭 |
| 第四章·王城裂隙 | 护符、召唤、全机制混编 | 护符、召唤、全怪物池 | 多阶段王城 Boss |

每章 5 关采用固定教学节奏：

1. **引入关**：只引入一个新机制，允许玩家看懂。
2. **检验关**：要求玩家主动使用对应技能或改变射击优先级。
3. **组合关**：新机制与旧机制组合。
4. **变体关**：加入战场规则、精英词缀或特殊出生方式。
5. **Boss 关**：综合考试，不再额外引入新规则。

单关目标时长控制在 3~5 分钟。主线通关只要求守住城墙；额外挑战不阻塞推进。

## 三、关卡内容语法

### 3.1 从“怪物数量”升级为“威胁预算”

为每种怪物配置基础威胁值，例如普通怪为 1，治疗、召唤、Boss 依机制提高。关卡先确定总威胁预算和压力曲线，再由编队消费预算。这样可以比较两套波次是否大致等价，而不是只比较总数量。

每波还需要标记压力类型：

- `swarm`：大量低威胁单位，检验范围伤害。
- `rush`：短时间高速突进，检验反应和控制。
- `siege`：远程与高血量单位，检验优先目标。
- `support`：治疗、护符、召唤形成保护链。
- `mixed`：章节后段的综合编队。
- `boss`：Boss 与护卫的阶段化战斗。

### 3.2 精英词缀优先于无限增加新怪

13 种基础怪已经足够形成职责矩阵。下一步先增加 4 个可读性强的精英词缀：

| 词缀 | 效果方向 | 玩家识别 |
|---|---|---|
| 巨化 | 更高生命与体型，移速略低 | 体型增大 + 厚重外圈 |
| 迅捷 | 移速与行为频率提高 | 明亮拖影 |
| 再生 | 一段时间未受伤后回血 | 绿色脉冲 |
| 号令 | 周围同伴获得小幅强化 | 旗帜/光环，必须优先击杀 |

词缀不能隐藏原怪物的核心弱点，也不能仅靠换颜色表达。每只精英最多一个词缀，Boss 使用独立阶段规则，不从普通词缀随机抽取。

### 3.3 战场规则与可选挑战

战场规则每关最多一个，并在开战前明确展示。首批只做能改变决策、实现成本可控的规则：双翼夹击、魔力涌动、逆风弹道、精英增援。

每关提供三个城防徽章：

1. 完成关卡。
2. 城墙剩余生命达到目标。
3. 一个关卡专属挑战，例如限定技能使用次数、优先击杀指挥怪或规定时间内完成。

徽章用于章节奖励和图鉴解锁，不作为下一关硬门槛，避免玩家因可选挑战卡住主线。

### 3.4 配置结构升级

现有 `waves.json` 只描述关卡、波次和出生组，生产 20 关后会难以维护。配置 V2 需要拆分为：

- `monsters.json`：生产默认数值、威胁值、职责、可用词缀。
- `chapters.json`：章节顺序、名称、规则池、解锁条件。
- `levels/*.json`：稳定 `levelId`、波次、预算、规则、挑战目标和奖励。
- `experiments.json`：可实验参数及默认变体，不直接复制整份关卡。

关卡存档必须从“第几个关卡”迁移到稳定 `levelId`，否则插入新关卡会破坏旧进度。配置加载要继续保持全量校验和安全回退。

### 3.5 内容生产与验收流水线

每批只制作 5 关，并经过同一流程：

1. 设计表写明教学目标、威胁预算、关键编队和预期时长。
2. 配置校验器检查未知怪物、非法数值、空波次、预算突变和不可达挑战。
3. 开发者工具支持按 `levelId` 跳关、指定实验组、快速胜负和查看威胁摘要。
4. 自动测试验证解析、预算、奖励、进度迁移和实验覆盖层。
5. 至少 3 名未看说明的玩家试玩；记录失败波次、技能使用、耗时和退出点。

## 四、长期玩法循环

```text
闯关游戏主页 -> 主线推关 -> 首通养成/徽章 -> 工坊成长 -> 下一关

肉鸽游戏主页 -> 无尽守城 -> 局内流派 -> 成绩 -> 局外养成/武器解锁 -> 下一局
             -> 每日挑战 -> 固定种子与规则 -> 当日奖励/分享
```

分层目标：

- **单局目标（3~10 分钟）**：守住本关或刷新无尽波数。
- **章节目标（约 30 分钟）**：完成 5 关、收集徽章、击败章节 Boss。
- **长期目标**：升级成长线、补全怪物图鉴、刷新好友成绩。
- **回访目标**：每日固定种子挑战；所有玩家面对同一编队与规则，成绩才可比较。

每日挑战应复用关卡规则、精英词缀和无尽波次生成器，不另写第三套战斗逻辑。

## 五、主菜单与页面结构

### 5.1 开发版入口（2026-11-18 已落地）

在正式主菜单建设前，开发构建先提供一个轻量玩法总入口，用来隔离不同玩法的数据生命周期和验证目标：

| 入口 | 当前用途 | 数据边界 |
|---|---|---|
| 玩法核心 | 使用五关拆分前已提交的独立 12 波基线，巡检射箭、基础技能、13 种怪物、波次与结算 | 火球/冰冻/箭雨仅在本局恢复可用；击杀收益、关卡进度、技能解锁和首通奖励全部不写入存档 |
| 闯关模式 | 五关战役、永久养成、首次通关随机奖励 | 正常读写玩家存档 |
| 肉鸽模式 | 无尽波次、每 3 波局内随机增益 | 当前正常结算击杀金币；武器掉落、解锁与独立局外养成仍在规划中 |

该入口只在 `CG_DEBUG_TOOLS=ON` 时出现，不能替代正式玩家菜单。开发版左上角常驻四宫格按钮，可从战斗、模式主页、工坊或结算返回此入口；跨游戏切换只属于内部开发导航，不进入任一游戏的通关弹窗或玩家菜单。关闭开发工具后，开发入口与四宫格按钮都由预处理剔除。

当前已经落地两套独立主页实例和最小生命周期：

```text
开发入口 -> 玩法核心 -> 直接战斗 -> 练习结算 -> 再次验证
         -> 闯关模式 -> 闯关主页 -> 战斗 -> 结算 -> 闯关主页
         -> 肉鸽模式 -> 肉鸽主页 -> 战斗 -> 结算 -> 肉鸽主页
```

两套主页可以复用无状态的排版组件，但必须分别持有页面实例、入口文案、功能入口和导航状态。现有正式构建的普通模式选择只作为 Demo 过渡入口；以后按独立游戏发布时，由构建产品直接进入对应游戏主页，不提供玩家侧跨游戏切换。

### 5.2 两套独立玩家菜单（待建设）

当前主页只完成最小开战闭环，尚不能承载章节选择、局外成长、装备、图鉴、排行、活动和设置。下一阶段分别建设两套完整游戏壳层：

```text
闯关游戏启动
└── 主城首页
    ├── 继续推关 -> 章节/关卡选择 -> 战斗 -> 结算 -> 主城
    ├── 工坊 -> 城墙/武器/技能/装备
    ├── 图鉴 -> 怪物/武器
    └── 设置 -> 音画/震动/隐私

肉鸽游戏启动
└── 守城营地
    ├── 新局/续局 -> 战前武器选择 -> 无尽战斗 -> 结算 -> 营地
    ├── 局外养成 -> 天赋/武器解锁/图鉴
    ├── 每日挑战 -> 固定种子 -> 成绩/排行
    └── 设置 -> 音画/震动/隐私
```

首页信息层级：

- 闯关主页主操作：继续当前主线，显示下一关和主要奖励；固定入口为主城、工坊、图鉴、设置。
- 肉鸽主页主操作：开始新局或继续中断局，展示武器配置与历史成绩；固定入口为营地、局外养成、图鉴、挑战、设置。
- 两个游戏可以复用存档、战斗和通用 UI 基础设施，但不得共享页面栈、返回目标或把另一游戏当作自身菜单项。

技术上将 `MainScene` 逐步收敛为战斗场景，不继续往里面堆页面。新增导航层统一传递 `BattleRequest`：模式、`levelId`、挑战规则和本局实验快照。结算页只产生结果和下一步意图，由导航层决定回主城、下一关或重开。

## 六、A/B 分组与灰度测试

### 6.1 两个概念必须分开

- **灰度发布**解决安全问题：先让少量用户使用新功能，观察崩溃、性能和严重异常，再逐步放量。
- **A/B 实验**解决决策问题：不同稳定用户组看到不同方案，用预先定义的指标判断哪个更好。

早期用户量小时，A/B 数据只用于发现明显方向，不能把几十人的差异当成统计结论。灰度回滚能力比“显著性”更优先。

### 6.2 稳定分组规则

分组不能使用每次启动重新随机。使用稳定玩家标识与实验 ID 做哈希：

```text
bucket = hash(playerId + experimentId + allocationSalt) % 10000
```

- 游客阶段生成并持久化本地安装 ID；接入微信身份后使用稳定的平台身份映射。
- 实验声明控制组、实验组、流量比例、开始/结束时间和配置版本。
- 同一实验在版本周期内保持分组；只有显式更换 `allocationSalt` 才重新洗牌。
- 用 `layer` 做互斥层，同一层一次只命中一个实验，避免多个数值实验互相污染。
- 开局时生成不可变 `ExperimentSnapshot`，战斗中远程配置变化不能改变正在进行的局。

V1 的包内清单与本地稳定分组只能验证分组算法、配置覆盖和测试流程。真正跨用户调流量、紧急关闭和无需发版回滚的灰度，必须接入远程配置服务；服务未接入前不能把本地分组称为线上灰度。

### 6.3 配置优先级与安全边界

```text
代码安全默认值 <- 包内配置 <- 已校验的远程配置 <- 当前实验变体覆盖
```

允许实验的参数必须进入白名单，例如首章出怪间隔、三选一触发波数、结算按钮布局。存档结构、资源任意发放、未完成页面和防沉迷逻辑禁止通过实验动态改变。

远程配置需要版本号、有效期、校验、最后一次可用缓存和一键关闭开关。下载或解析失败时回到包内安全值，不能阻塞玩家进入游戏。

### 6.4 曝光与事件

“被分到实验组”不等于“看到了实验”。只有玩家真正进入相关页面或开始对应关卡时才记录曝光。

首批事件：

- `session_start`、`home_view`、`mode_start`。
- `stage_start`、`wave_fail`、`stage_end`、`run_quit`。
- `reward_offer`、`reward_select`、`upgrade_purchase`。
- `endless_end`、`daily_end`、`share_result`、`ad_result`。

公共字段：匿名玩家 ID、会话 ID、客户端版本、配置版本、实验快照、模式、`levelId`、设备性能档。事件不记录昵称、聊天或其他非必要个人信息。

核心指标：

- 新手：进入首页到首次开战的转化、第一关完成率、首次失败点。
- 关卡：开始率、通关率、尝试次数、中途退出率、耗时、剩余城墙生命。
- 战斗：技能使用率、主要伤害来源、失败波次、帧率分位数。
- 长期：次日回访、章节完成、无尽重复游玩、分享和广告完成率。

### 6.5 首批实验建议

一次只运行一个高影响实验：

1. 首页“继续推关”入口位置与信息量，目标是缩短首次开战时间。
2. 第一章难度曲线，比较保守版与标准版的第 1~5 关完成率和退出率。
3. 无尽增益间隔：每 3 波与每 4 波，观察局长、流派成形速度和重复开局率。
4. 首通奖励池权重，观察选择分布与后续升级行为。

长按连射、触摸修复、崩溃修复和合规功能属于基础质量，不进入 A/B。

## 七、实施顺序与验收

### P0：冻结当前可玩基线

- 提交当前 M1/M2 V1 功能，打可回退标签。
- 固定存档迁移测试、桌面/WASM/正式构建基线。

### P1：独立游戏菜单壳层

- 闯关游戏完成主城、章节入口、工坊、设置占位与返回链路。
- 肉鸽游戏完成营地、新局/续局、局外养成、武器解锁、设置占位与返回链路。
- 战斗通过 `BattleRequest` 启动，退出后稳定返回发起战斗的游戏主页；两套页面栈互不跳转。
- 验收：两个独立构建中，陌生玩家都能从启动完成各自的“主页 → 成长/配置 → 战斗 → 结算 → 主页”闭环，不依赖开发入口。

### P2：实验与埋点底座 V1

- 包内实验清单、稳定本地分组、互斥层、实验快照、调试强制分组。
- 本地事件队列与可读日志；网络上报接口先抽象，接平台时再实现。
- 验收：重启分组不变，非法配置回退，同一局参数不漂移，控制组行为与当前版本一致。

### P3：战斗成长与装备 V2

- 统一属性、Buff、限时状态和伤害来源结算。
- 完成全局弓术研究、武器换装、城墙本体、被动设施和武器站驾驭系统。
- 验收：旧存档不丢成长，局内 Buff 不污染永久数据；玩家接管一个武器站时，其余武器按规则自动攻击且切换不刷新装填。

### P4：内容配置 V2

- 稳定 `levelId`、章节拆分、怪物威胁值、精英词缀、战场规则、挑战目标。
- 配置校验器与自动测试；旧存档迁移不丢当前进度。

### P5：20 关与每日挑战 V1

- 分四批各制作 5 关，每批独立试玩和调参。
- 完成 4 个精英词缀、4 个战场规则、章节 Boss 和怪物图鉴。
- 每日挑战使用固定种子，先本地生成，排行榜接入后再比较好友成绩。

### P6：社交、商业化与性能

- 好友排行榜、战绩分享卡片、激励视频。
- 同屏 100+ 实体压测和中低端安卓 50fps+ 验收。
- 最后进入备案、提审、上线与种子用户复盘。

## 八、明确暂不做

- 不在 Axmol 阶段建设完整跨端账号与自有运营后台。
- 不一次性制作 50~100 个手工关卡。
- 不同时运行多个会影响战斗数值的实验。
- 不让 A/B 配置直接修改存档协议、付费结果或合规逻辑。
- 不为每日挑战复制一套战斗代码。

这套边界保证第一站仍以微信小游戏真实上线为终点，同时让内容、菜单和实验协议可以在 Unity 版本继续复用。
