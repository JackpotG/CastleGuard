## 数学 · 向量

### Q：normalize 是什么意思？（2026-11-16）

**一句话**：把向量缩放到长度恰好为 1、方向不变，剥掉"距离"只留"方向"。

**详解**：
- 点击位置离发射点有远有近，`(target - archer)` 的长度不固定；直接当速度会"点得远箭速快"，手感混乱
- 归一化后长度恒为 1（单位向量），再乘以想要的速率：`速度 = 方向 × 1000`，箭速与点击距离解耦
- 公式：`v̂ = v / |v| = (x, y) / √(x² + y²)`
- 边界：零向量不能归一化（除以 0 → NaN，坐标崩坏），代码里用 `lengthSquared() < 1.0f` 提前拦截
- 性能习惯：比较长度用 `lengthSquared()`（不开根号），每帧跑的逻辑里开根号能省则省

**关联**：`code/axmol/CastleGuard/Source/MainScene.cpp` → `fireArrow()`

**延伸可学**：点积（dot）判朝向/夹角、叉积（cross）判左右、lerp 插值做平滑跟随

## 游戏设计 · 架构

### Q：Boss 自由飞、怪物会换线/从别的方向进，是不是就不需要"车道"概念了？（2026-11-16）

**一句话**：车道要保留，但从"运动规则"降级为"逻辑层的配置工具"，怪物移动交给各自的行为组件。

**详解**：
- 车道的真正价值在逻辑层：① 波次配置的维度（哪线出怪 = 压力分布与难度曲线）；② 玩家心智模型（威胁可读、能预判，原作的车道预警箭头）；③ 与命中判定无关——圆碰撞（箭尖点 vs 怪身圆）天然支持任意位置
- 拆法：**逻辑层（车道）与表现层（移动行为）解耦**。`lane` 只作"出生初始车道 / 换线目标参考"，移动抽成 MovementBehavior：
  - 普通怪：沿车道直线（现状不变）
  - 换线怪：受击/攻击后换目标车道，插值平滑滑过去
  - Boss：waypoint 巡逻或追踪，完全忽略车道，可前进可后退
- 出生点参数化：`SpawnConfig { 位置, 方向, 目标 }`，不再钉死出怪口 → "从其他方向进入"只是改配置
- 与波次管理（JSON 驱动）是同一个设计的两半：波次 JSON 里每只怪带 `type`，`type` 决定移动行为
- 通用原则：**数据与行为分离**——配置描述"出什么、从哪出"，行为组件决定"怎么动"

**关联**：`code/axmol/CastleGuard/Source/MainScene.cpp` → `spawnMonster()` / `laneSpawnPos()`；docs/03 开发清单"波次管理"项

**延伸可学**：状态机（已用于 Walk/Attack/Dead）、策略模式（行为组件的本质）、steering behaviors（追踪/逃逸/巡逻的经典算法）

### Q：技能的额外效果（麻痹/减速）需要单独做系统吧，不能像现在这样用计时器裸逻辑？（2026-11-17）

**一句话**：对——裸计时器是刻意的临时简化，正规做法是 Buff 系统（修饰器模式），清单把它排在 M2 三选一之前做。

**详解**：
- 裸计时器（`stunTimer`/`slowTimer` 直接改属性）的四个坑：
  1. **叠加规则没法表达**：两个减速同时命中，取最强/叠加/刷新？裸实现只能粗暴重置
  2. **没有来源概念**：无法"只驱散冰冻的减速、保留其他效果"
  3. **属性改不回去**：直接改字段，效果结束时想恢复原值就得祈祷没人动过它
  4. **表现同步靠手工**：黄电纹/蓝环标记要手动对齐计时器生命周期，容易漏
- 正规形态：怪物身上挂 `vector<Buff>`（类型/剩余时间/强度/层数/来源），update 统一 tick；移速、攻击力等属性**每帧由基础值 + buff 修饰器链算出来**，永不直接改
- 为什么现在不做：**需求驱动设计**——当前只有 2 个 debuff，护盾怪的"免箭"是静态特性、自爆怪的"死亡触发"也不依赖 buff 框架；M2 的 Roguelike 三选一才会让增益爆炸式增长，那时框架才有据可依
- 这也是一次"技术债"的正面教材：知道是债、注释标明、排期偿还（M2 重构），比过度设计或蒙头乱写都健康

**关联**：`code/axmol/CastleGuard/Source/MainScene.cpp` → `castSkill()` 闪电/冰冻分支的注释；docs/03 开发清单 M2「Roguelike 三选一 —— Buff 系统设计（修饰器模式）」

**延伸可学**：修饰器模式（Decorator）、ECS 中的组件化状态、技能系统数值表驱动（策划改表不改代码）

## 引擎 · 基础概念

### Q：通过 Codex 启动桌面版时为什么总要求访问“文稿”，是权限还是启动方式问题？（2026-11-20）

**一句话**：是存档路径触发的 macOS 文件权限提示；Axmol 默认把 Apple 平台的可写目录放在“文稿”，换一种启动方式不能消除这次目录访问。

**详解**：
- 桌面版 `GameData` 用 `UserDefault` 读写进度；`UserDefault` 取 `FileUtils` 可写路径，而 Axmol 默认返回 `~/Documents/`
- macOS 保护“文稿”目录，应用访问时会提示授权；由 Codex 发起启动时，系统还可能把请求归因到 Codex
- 桌面版入口现在先创建 `~/Library/Application Support/<bundle id>/` 并调用 `setWritablePath()`，然后才进入游戏或测试，存档不再要求“文稿”权限
- 旧存档若在 `~/Documents/UserDefault.bin`，需要用户主动迁移一次；自动读取旧目录会再次触发提示

**关联**：`code/axmol/CastleGuard/proj.ios_mac/mac/main.mm` → `configureWritablePath()`；`code/axmol/CastleGuard/Source/GameData.cpp` → `readStoredInt()`；`engine/axmol/core/platform/apple/FileUtils-apple.mm` → `getNativeWritableAbsolutePath()`；docs/04 排雷 4.1

**延伸可学**：macOS 的 TCC 隐私权限、应用专用数据目录、存档迁移与兼容策略

### Q：Axmol 是什么？是做什么用的？为什么代码放在 code/axmol/ 下？（2026-11-16）

**一句话**：Axmol 是 Cocos2d-x 的社区继任者——开源 C++ 跨平台 2D 游戏引擎；`engine/` 放引擎（工具，第三方，不入库），`code/` 放游戏工程（作品，我们的资产，入库），工具与作品分家。

**详解**：
- 引擎 = 搞定"每个游戏都要重写一遍"的底层杂务：场景图（Scene/Node 树）、主循环（`update(delta)`）、渲染（DrawNode 背后是真 GPU 调用）、输入事件、资源管理（FileUtils）、跨平台编译
- Axmol 的身世：Cocos2d-x 官方停更 → 社区分叉出 Axmol 继续维护（修 bug、支持新系统、新增 Vulkan/Metal 渲染后端）
- 为什么选它：微信官方 wx-transformer 支持 Cocos2d-x 系 → Axmol→WASM→小游戏链路可行；C++ 裸引擎无编辑器黑盒，对象池/状态机都要手写——对学习是优点
- 目录分家的两个原因：① 引擎 1.5GB 第三方代码可随时删了重拉（docs/04 有重建步骤），游戏代码才入库；② 三引擎路线（Axmol→Unity→UE）下 `code/` 按引擎分目录，同一玩法三种实现可对照学

**关联**：`code/axmol/CastleGuard/Source/MainScene.h`（Scene 子类）；docs/01 技术路线备忘；docs/04 工具链讲解

**延伸可学**：游戏引擎 vs 游戏框架的区别、场景图（scene graph）为什么是现代引擎的标配、Unity/UE 的组件模式与本项目手写面向对象的对比

### Q：箭看起来从弓前方发射，是因为弓把发射箭盖住了吗？（2026-11-18）

**一句话**：不是遮挡，而是飞行箭在第一次被画出来前已经叠加了“出生前移 + 首帧飞行”两段位移，所以肉眼看到时它已经离开弓弦。

**详解**：
- 层级可以先排除：待发射箭以 `zOrder 1` 画在弓身之上；真实飞行箭以场景 `zOrder 3` 画在整个战场容器之上，弓不会盖住它
- 当前出生点沿射击方向预先前移 `24` 像素，用来让箭节点的尾部靠近弓弦；但箭从输入事件中激活后，可能在本帧渲染前先进入 `updateArrows()`
- `updateArrows()` 立即执行欧拉积分：`新位置 = 旧位置 + 速度 × delta`。箭速为 `1000 px/s` 时，60 FPS 的首帧还会移动约 `1000 × 1/60 ≈ 16.7` 像素
- 两段位移叠加后，玩家第一眼看到的飞行箭已在弓前方；同时待发射箭已隐藏，视觉上就出现了中间断层
- 最终实现让对象池里的真实箭在装填时直接成为弓的子节点，发射时保留世界坐标重新挂到场景并开始飞行；弓上箭和飞行箭是同一个对象，因此不再需要复制表现或用“刚发射”标记衔接两个对象

**关联**：`code/axmol/CastleGuard/Source/MainScene.cpp` → `fireArrow()` 的出生位置、`initArrowPool()` 的 `zOrder`、`updateArrows()` 的首帧积分

**延伸可学**：固定时间步与可变时间步、逻辑更新和渲染的先后顺序、弹体的出生阶段状态机、视觉位置与碰撞位置分离

## 原作 · Defender II 考据

### Q：原版游戏的三个技能分别是什么？（2026-11-17）

**一句话**：原作不是固定 3 个技能，而是火/冰/电**三系魔法塔、每系 3 阶递进**——战斗中的 3 个技能位 = 三系各带当前等阶的法术。

**详解**（来源：百度贴吧玩家满级存档数据 + 百度百科玩法介绍）：
- 火系：火球 → 流星 → 末日审判
- 冰系：冰锥 → 冰霜新星 → 冰河世纪
- 电系：闪电 → 闪电风暴 → 诸神的黄昏
- 升级魔法塔逐阶解锁；弓箭侧的"多重箭/致命一击/毒箭"是升级线，不占技能位
- 交互是**拖放法术图标释放**——我们 M1 的"按住按钮拖动、抬起释放"与原作一致

**我们的取舍**：清单定的「火球 / 冰冻减速 / 箭雨」是简化版——火球、冰冻对应原作火/冰系
1 阶，箭雨是自研（把原作弓箭侧"多重箭"的爽感挪进了技能位）。后续局外升级可以
引入"系别 + 等阶"的递进结构（docs/01 的局外升级界面任务）。

**关联**：`docs/01-项目上下文.md`（原作分析）、`MainScene.cpp` 技能系统（`castSkill`）

## 工具 · 技能树布局

### Q：为什么城防营没有军械所的摆放、连线等配置，怎样让所有技能树通用？（2026-11-25）

**一句话**：城防营残留了早期横向等级分支的特殊实现；设施应只是数据分类，共用节点编辑、布局、校验和绘制流程。

**详解**：

- 只让页面看起来相同还不够：工具曾跳过城防营的位置设置和部分层级校验，游戏又忽略其配表位置，按每一级横向展开。两端都要移除例外，保存的配置才能在游戏中生效。
- 通用配置管理稳定 ID、层级与横向位置、多前置及各自等级、价格和效果。军械所、研究院、城防营通过 `track` 分类，不应各自复制节点和连线实现；属性效果由配表选择。
- “一个节点”代表一项可逐级投入的研究，不代表固定的某一级。点击节点购买下一级，所有前置必须同时达到要求；价格数量决定最大等级。
- 法术也共用摆放、预设和连线，但法术的“解锁”与被动属性的“升级”保留各自含义。复用展示和布局不等于把不同玩法强行当成相同效果。
- 旧城防配置缺少位置时先在内存补齐，主动保存才写回；稳定 ID 不变就能继续读取原等级。通用界面不会自动创造魔法塔等尚未实现的战斗机制。

**关联**：`tools/config-editor/upgrade-editor.js` / `tree-position.js` → 共用配置与位置预设；`code/axmol/CastleGuard/Source/UpgradeCatalog.cpp` → 兼容读取；`UpgradePanel.cpp` → 共用节点与连线；`docs/10-技能树配表协议.md`。

**延伸可学**：数据驱动、公共模型与表现层、旧配置迁移、编辑器与运行时的一致性测试。

### Q：技能树同层只能放 3 个节点吗？（2026-11-25）

**一句话**：当前横向范围和最小间距允许同层最多放 5 个节点，4 个节点均分时报越界是浮点计算误差。

**详解**：

- 可用范围为 0.12–0.88，宽度 0.76；最小间距为 0.18，因此最多放 `floor(0.76 / 0.18) + 1 = 5` 个节点。
- 计算机使用二进制近似存储小数；四节点均分时，最右坐标可能算成 `0.8800000000000001`，严格范围检查就会误判越界。工具把生成的均分坐标保留 6 位小数，再交给原来的范围与间距检查。
- 超过 5 个需要重新设计布局宽度或间距，并同步工具与游戏的校验规则；只放宽工具提示不能让游戏正确读取配置。

**关联**：`tools/config-editor/tree-position.js` → `plan()`；`docs/10-技能树配表协议.md` → 布局范围；`code/axmol/CastleGuard/Source/GameData.cpp` → 游戏端位置校验。

**延伸可学**：浮点误差、边界校验、编辑器与运行时的数据约束一致性。

### Q：多前置节点与其他分支共用横线会混淆，有什么更清楚的连线方案？（2026-11-25）

**一句话**：采用“派生合并、接入拆分”，同一父节点的分支共用出线，不同前置分别接入目标的独立位置。

**详解**：

- “位于同一层间区域”与“共用同一条线”是两回事；力量与敏捷的线路完全重叠后，玩家可能把整条横线当成共同前置，误以为鹰眼、强力一击、多重箭也都需要这两个属性。
- 派生合并：力量派生鹰眼、强力一击和新节点时，可从同一主干分叉；同父线路可以共享这一段，因为来源明确。
- 接入拆分：新节点同时要求力量和敏捷时，两条线保持独立线段和不同入口；不会在节点外合成一条线，其他三个单前置节点也不会被视觉上接到这组条件里。
- 同层折线优先共用高度基准，不按来源人为错开高度。“同高”只约束排版，不代表线路相连；例如两个前置入口上方留有空隙，就能同时做到整齐和关系独立。实际遮挡或线路重叠时仍需绕行。
- 纵向树按来源的左右位置排列接入口，横向链按上下位置排列；调整前置列表顺序不会任意交换入口。跨层依赖仍避开中间节点及文字。
- 无关线路无法完全错开时，在交叉位置留断口；不同来源不允许共用重叠线段。名称阻挡出线或空间拥挤时允许独立绕行，目标入口仍保持拆分。
- 独立曲线、带“全部满足”的汇合菱形、选中高亮都是可选方案；本次采用参考图的直接拆分接入方式。实现只调整绘制，配表仍要求所有前置同时满足，不增加可升级节点或存档数据。

**关联**：`code/axmol/CastleGuard/Source/TreeConnectionRouter.cpp` → `mayJoin()` / `makeBands()`；`tools/config-editor/app.js` → `drawTreeConnections()`；`docs/10-技能树配表协议.md` → 跨层级连线。

**延伸可学**：有向图与超边、AND 条件的可视化、线路交叉与连接点的区别、按依赖子图高亮。

## 工程 · 构建开关

### Q：返回开发模式页的控件，仅限 Debug 模式才会显示吗？（2026-11-18）

**一句话**：是；“返回开发入口”只在 `CG_DEBUG_TOOLS=ON` 的常驻 ImGui 面板中存在，正式构建不会编译面板及其操作逻辑。

**详解**：
- `CMakeLists.txt` 把 `CG_DEBUG_TOOLS` 注入为 C++ 预处理宏；日常开发默认开启，提审和发布时必须显式关闭
- ImGui 面板的注册、绘制和操作都位于 `#if CG_DEBUG_TOOLS ... #endif` 内；关闭后，编译器在编译前就会删掉这些代码
- 开发模式选择页和其他调试工具使用同一开关，因此正式包里无法通过误触或隐藏热区进入开发菜单
- 2026-11-19 将旧版左上角独立按钮整合进常驻 ImGui；条件编译比运行时隐藏更彻底，正式二进制没有该功能

**关联**：`code/axmol/CastleGuard/CMakeLists.txt` → `CG_DEBUG_TOOLS`；`code/axmol/CastleGuard/Source/MainScene.cpp` → `onEnter()` / `drawDevelopmentControlTab()`

**延伸可学**：C/C++ 预处理与条件编译、Debug/Release 与功能开关的区别、为什么发布包要做“零残留”验证

## 渲染 · 2.5D 建筑

### Q：怎样让梯形屋顶同时看出前后坡和左右侧面？（2026-11-19）

**一句话**：让整个屋顶保持上窄下宽的梯形外轮廓，用屋脊横线和通向四角的斜线在内部划出前坡、后坡、左侧面和右侧面。

**详解**：
- 前檐是梯形下边，后檐是上边，屋脊在两者之间且短于后檐；外边从后檐角直接连到前檐角，中途不能向内凹
- 屋脊两端分别向同侧的前后角连线，形成两个梯形坡面和两个三角形侧面；侧面占的是屋顶内部的面积，不是叠在坡面上的窄条
- 前坡纵深略大于后坡，更符合当前从城内略微向下看的投影；用明暗区分四面，再以细线强调边界，不额外画横向瓦线
- 这些屏幕比例服务当前的小型设施画法；改变建筑大小或视角后，应重新检查四面的可读性

### Q：为什么烟囱和塔楼会看起来立在屋后地面上？（2026-11-19）

**一句话**：屋顶附属物的底座必须落在可见屋面内，并在屋面之后绘制出接触与遮挡；缩短正面墙、增加可见屋面纵深，也会加强俯视感。

**详解**：
- 先画附属物再画屋顶时，屋面会盖住其下半部，只剩屋后露出的顶端，视觉上便像建筑背后的独立物体
- 烟囱和塔楼改为从后坡内部的底座向上长出，底座周围画一小块较暗的接触面，墙身覆盖屋面一部分，明确两者相接
- 屋檐线下移后，正面墙的可见高度缩短，屋顶纵深相对增加；但屋顶过大又会让视角显得过高，因此当前比例适度上移屋檐线，让立面多露出一些
- 调整屋檐线时，门窗要同步伸缩到墙面范围内，烟囱和塔楼底座也须继续落在后坡内部
- 如果目标是缩小屋顶本身的投影面积，应分别收窄屋顶横向宽度和前后纵深，而不是只抬高屋檐线；军械所单独调整屋面，正面墙保持原尺寸
